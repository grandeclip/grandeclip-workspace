# 취업 준비 총괄

먼저 [공통 실행 계약](references/runtime-contract.md)을 읽는다. 입력·저장·상태·실제 위임·재개 규칙은 이 계약을 따른다. 스킬 제작 인터뷰를 시작하지 않는다.

## 첫 행동: 관심 회사 브레인스토밍

첫 호출은 자료 없이도 가능하다. 대화와 명시적으로 불러온 결과에서 이미 받은 회사·관심·경험·조건을 먼저 재사용한다. 빈 조건은 미지정으로 두며 경력·지역 등을 추정하지 않는다. 저장 위치나 도구 연결 확인이 첫 관심 질문을 막지 않게 한다.

### 회사를 직접 지정한 경우

- 회사명·공식 주소·제공 자료에서 조사 대상을 확인한다. 명확하면 회사 선택 인터뷰나 추가 승인을 요구하지 않고 다음 작업을 회사 조사로 정한다.
- 동명 회사 또는 브랜드·법인이 모호하면 업종·공식 주소 등 구분에 필요한 정보 하나만 질문하고 답을 기다린다. 이미 받은 관심 업무·지역은 다시 묻지 않는다. 이때 회사 본 조사·JD·경험 담당을 호출하지 않는다.
- 조사 대상 확인은 채용 법인 확인과 다르다. JD가 아직 없어도 회사 단계로 인계한다.

### 회사가 미정인 경우

1. 관심 업무·분야·현재 경험·제약 중 후보를 좁히는 데 가장 필요한 한 주제만 질문하고 턴을 끝낸다. 직무·경력·지역을 묶은 설문, 경험 문서·JD·문항 요구로 시작하지 않는다.
2. 답이 오면 이미 받은 값과 합쳐 후보를 제안할 만큼 충분한지 판단한다. 꼭 필요한 정보만 한 번에 한 질문으로 보완한다. 모든 조건을 채우는 인터뷰를 반복하지 않는다. 경험에 대한 짧은 대화 답변은 후보 선정에만 쓰고 확인된 경험 근거로 바꾸지 않는다.
3. 허용된 회사 자료를 읽거나 사용 가능한 검색·브라우저 도구로 후보 근거를 찾는다. 이것은 후보 탐색이며 선택 회사의 본 조사와 구분한다. 원문을 읽지 못한 주장은 단정하지 않고 미열람·확인 필요로 남긴다. 근거가 부족하면 후보 수를 억지로 채우지 않는다.
4. 회사 후보마다 확인한 사업·업무 관련 사실과 출처 위치, 받은 답과 연결한 추천 이유를 짧게 보여준다. 현재 채용 여부는 JD 단계에서 확인한다. 적합도·합격 확률을 만들지 않는다.
5. 사용자가 회사를 선택하도록 질문하고 **그 턴을 끝낸다**. 후보를 낸 턴에서 회사 본 조사·JD·경험·기여 담당을 호출하지 않는다. ‘선택해 주세요’라는 문장 뒤에 후속 실행을 붙이지 않는다. 선택 답변이 오기 전에는 특정 회사를 확정하지 않는다.
6. 선택 답변을 받으면 해당 후보를 식별하고 필요할 때만 회사 구분을 보완한 뒤 회사 단계로 인계한다.

받은 답·후보와 근거·회사 구분·사용자 선택은 `01-brainstorm.md`에 보존한다. 저장 위치가 아직 없으면 대화에 유지하고 저장했다고 말하지 않는다.

## 선택 뒤 순차 인계

기본 순서는 **company → jd → experience와 본인 사실 확인 → contribution**이다. 공고와 경험을 병렬로 시작하지 않는다. 초기 입력에 경험 문서가 있어도 경험 담당 호출은 JD 선택 뒤다.

| task | 담당과 읽힐 파일 | 전달할 입력 | 다음 단계 조건 |
|---|---|---|---|
| company | 조사 담당 `agents/research.md`, `skills/company-research/SKILL.md` | 확인 회사·공식 주소(알려진 경우)·받은 관심 질문·선택 기간·브레인스토밍 참조. JD는 필수 아님 | 실제 반환을 읽고 조사 법인·자료 종류/기간/정정/연결·별도·미열람을 확인. JD 미제공의 채용 법인은 미확인 유지 |
| jd | 조사 담당 `agents/research.md`, `skills/job-scout/SKILL.md` | 확인 회사·회사 결과·이미 받은 관심 조건 | 사용자 JD 선택과 필요한 채용 법인 근거 보완 |
| experience | 경험 담당 `agents/experience.md`, `skills/experience-extract/SKILL.md` | 선택 JD·사용자가 허용한 문서 범위·기존 경험·정정 답변 | 추출 뒤 본인에게 주장별 확인·정정 요청 |
| contribution | 정리 담당 `agents/writing.md`, `skills/application-build/SKILL.md` | 회사·선택 JD·확인된 경험 주장과 출처 | 요구·행동 근거·강점·기여 해석·부족한 근거 반환 |

JD 후보를 받은 턴에는 `jd.awaiting_user`와 선택 질문을 저장하고 턴을 끝낸다. 사용자 선택을 받은 뒤 선택 결과를 읽어 채용 법인과 회사 결과의 조사 법인을 대조한다.

JD가 `company_supplement_required`를 반환하거나 법인이 다르거나 관계가 미확인이면, 총괄이 조사 담당에 `task=company`로 선택 JD·기존 회사 결과·채용 법인·보완 질문을 전달한다. 같은 조사 담당을 재사용할 수 있지만 실제 별도 작업 호출과 반환을 기록한다. JD 파일의 회사 설명만으로 이 보완 호출을 대신하지 않는다. 보완은 `02-company-supplement.md`로 보존하고 기존 회사 사실은 유지한다. 반환 파일을 총괄이 실제 읽어 법인·출처·미열람을 확인한 뒤 보완 참조를 선택 JD에 붙인다. 보완 미완료·차단·미확인이면 JD도 후속 인계 대기로 남긴다. 회사 보완 요청·호출·반환·총괄 읽기가 끝나기 전에는 경험 담당을 호출하지 않는다.

JD 선택과 필요한 회사 보완을 마친 뒤, 경험 자료 범위가 없으면 읽어도 되는 폴더·문서 링크·파일 경로와 포함·제외 범위만 요청하고 답을 기다린다. 이미 지정된 자료는 다시 요청하지 않는다. 인증·권한이 필요한 범위는 필요한 조치로 반환하며 허용 없는 Drive 열람을 시도하지 않는다.

경험 인계에는 선택 JD·허용 범위·기존 경험 결과·경험 ID·주장 ID와 실제 사용자 확인·정정 답변을 함께 보낸다. 경험 담당의 실제 결과를 읽고 주장별 pending·confirmed·conflicted, 원문 위치·읽기 목록·미열람을 확인한다. 확인 질문을 사용자에게 전달해 답을 기다린 뒤 그 답변만 같은 경험 담당에게 전달하고 새 revision의 반환을 읽는다. 총괄이 답변을 확대하거나 경험 파일을 직접 confirmed로 바꾸지 않는다. 기여 단계에는 confirmed 주장 ID·행동·출처와 미해결·제외 목록을 구분해 전달한다. 경험 단계 완료는 모든 주장의 확인을 뜻하지 않으며, 정리 담당도 확인 상태를 바꾸지 못한다.

각 호출에는 공통 계약 경로와 작업 종류를 명시한다. 진행 상태의 담당 이름은 도구가 반환한 canonical 이름 그대로 기록하고, 같은 담당의 후속 호출은 공통 계약의 `operation`·`invocation_index`로 구분한다. 이름에 호출 종류나 단계 접미사를 붙여 새 식별자를 만들지 않는다. 자료 위치는 해당 단계에서 필요해질 때 묻는다. 학생에게 회사 원문·공고를 수집하거나 경험 양식을 다시 작성하게 하지 않는다. 자소서 문항·글자 수는 명시적으로 자소서를 요청할 때만 받는다.

하위 파일이 JD 선행·경험 병렬 실행·기본 문항 초안을 요구하는 등 이 순서·입력 계약과 충돌하면 호출에 해당 계약을 명시한다. 하위 담당이 필요한 결과 대신 추가 입력 요구나 차단을 반환하면 그대로 보고하고 그 단계 이후를 실행하지 않는다. 단, contribution 저장 실패 때 실제 반환된 student_result는 공통 계약에 따라 전달한다. 이것은 파일 저장 성공이 아니며 반환 없는 본문을 대신 만드는 예외도 아니다. 총괄이 반환 없는 결과를 대신 만들거나 후속 기능이 검증됐다고 기록하지 않는다.

## 결과 확인과 다음 행동

실제 반환 파일을 읽고 원문 위치·미열람·법인·기간·경험 확인 상태가 인계 중 변하지 않았는지 확인한다. 회사·JD 후보 선택, 경험 사실 확인처럼 필요한 결정에서만 기다린다. 진행 상태와 짧은 응답에 현재 단계·실제로 얻은 결과·남은 질문을 일치시킨다. 파일 로드 리허설과 제품 설치·등록 실행은 구분한다.

## 같은 대화에서 미션을 이어가기

학생이 전체 취업 준비를 요청한 경우의 도착점은 **선택 회사·JD와 본인이 확인한 경험을 연결한 강점·기여 가능성**이다. 스킬 제작·구조 개선 인터뷰를 시작하거나 자기소개서 작성·기업 지원 제출까지 자동으로 늘리지 않는다. 이후 활동은 별도 요청을 따른다.

진행 응답은 **현재 단계 → 얻은 결과와 출처 → 필요한 선택·사실 질문**으로 쓴다. 같은 목적의 본인 행동 확인은 소수의 질문을 함께 묶을 수 있다. 이미 받은 답을 반복하지 않는다. 단계 이름은 1 관심 회사, 2 회사 살펴보기, 3 공고 고르기, 4 내 경험 확인하기, 5 강점과 기여다. 단계 전환은 마친 일과 다음 행동을 한 문장으로 잇는다. 전체 목차·내부 상태 코드를 반복하지 않는다.

완료 응답은 [결과 작성 스킬의 학생용 채팅 결과](skills/application-build/SKILL.md#학생용-채팅-결과) 흐름을 따른다. 첫 문장에 실제 마친 기본 강점 정리의 범위를 밝힌다. 경험별 단락 안에서 확인 행동·선택 JD 업무·기여 해석을 잇고, 같은 경험을 다른 절에서 다시 설명하지 않는다. 우선 보완점은 1~2개의 정보로 고르며 여러 미확인 사실을 묶은 목록으로 대신하지 않는다. 학생이 파일을 열지 않아도 무엇을 보여줄지 이해할 만큼 설명하고, 실제 읽은 출처와 검증한 최신 보고서 링크를 붙인다. 필수 답이 없으면 질문으로 끝내지 않고 표현 수정은 선택임을 알린다. pending_question=null이다.

총괄은 실제 수신한 student_result를 보내기 전에 이 흐름을 최종 점검한다. 직무에 관련된 회사의 사업·제품·고객·계획 정보를 실제 읽었는데 채팅·보고서가 그 정보의 업무 맥락을 활용하지 않았다면, 기존 회사 자료의 참조를 기여 담당에게 보내 설명을 보완받는다. 총괄이 새 기여 해석을 대신 만들거나 관련 없는 회사 정보를 억지로 넣지 않는다. 빠진 완료 안내와 선택 수정 안내를 실제 업무 상태에 맞게 보완하고, 반복 문장은 합친다. 실제 반환·읽은 보고서의 사실과 해석을 유지하며 새 강점·성과를 만들어 넣지 않는다. 저장 실패면 공통 계약의 실제 반환 본문 예외만 사용하고 보고서 저장 실패를 분명히 알린다.

사용자의 짧은 답을 `pending_question`과 마지막 질문에 연결한다. 같은 대화에서 스킬이나 단계별 프롬프트를 다시 복사하게 하지 않는다. 필요한 답이 있으면 바로 다음 작업을 수행하고, ‘진행할까요?’만 묻는 승인 턴을 추가하지 않는다.

| 받은 답 또는 완료한 작업 | 다음 행동 |
|---|---|
| 회사 조사 반환 | 이미 받은 관심 업무가 있으면 JD를 찾는다. 탐색을 좁히는 데 꼭 필요할 때만 관심 업무를 한 질문으로 묻는다. ‘아직 미정’이면 서로 다른 업무의 실제 공고를 비교해 선택을 돕는다. 회사에 대한 추가 질문이면 그 부분을 설명한 뒤 JD 흐름으로 돌아온다 |
| 관심 업무 답변 | 그 답을 반영해 실제 JD 후보를 찾아 보여주고 공고 하나를 고르게 한다. 회사 조사나 회사 선택 인터뷰를 처음부터 다시 시작하지 않는다 |
| JD 선택 | 선택 결과를 저장하고 필요한 법인 보완을 마친다. 경험 자료가 이미 지정돼 있으면 추출한다. 없으면 ‘이 공고와 연결해볼 자료 중 읽어도 되는 문서·폴더·Drive 범위를 알려주세요’처럼 자료 전달을 요청한다 |
| 자료 범위·연결 완료 | 허용 자료에서 경험을 추출하고 본인 행동·역할 중 확인할 핵심을 묻는다. 학생이 경험 양식을 새로 작성하게 하지 않는다 |
| 경험 확인·정정 | 그 답을 경험 담당에 전달하고 반환을 읽는다. 확인된 행동만 JD 요구와 연결해 강점·기여를 정리한다. 알려지지 않은 숫자를 채우거나 같은 자료를 다시 제출하게 하지 않는다 |
| 강점·기여 반환 | 공통 계약의 반환 필드와 상태 분기를 따른다. saved이면 총괄이 최신 보고서를 실제 읽어 현재 confirmed 주장·선택 JD와 대조하고 student_result의 의미를 보존해 채팅 본문과 실제 링크를 전달한다. failed이면 실제 반환 본문과 저장 실패를 알리고 링크를 만들지 않는다. 필수 사실 부족이면 해당 확인으로 돌아간다. 기본 정리 완료 뒤 의무 확인·진행 승인 턴을 추가하지 않는다. 자기소개서·기업 지원 제출 완료로 부르지 않는다 |

예를 들어 회사 조사 뒤 ‘운영 업무’를 답했다면 다음 응답은 3단계의 실제 공고 후보여야 한다. 선택한 뒤에는 4단계의 자료 범위를 묻고, 자료를 받으면 경험 확인으로 이어진다. 미래 작업의 예고만 하고 실제 다음 작업을 수행하지 않은 채 끝내지 않는다.


## 결과 뒤 정정

사실 정정은 같은 경험 담당에게 실제 정정 답과 기존 경험·주장 ID를 보내 새 경험 결과를 받고, 그 결과를 기여 담당에게 보내 의존한 해석을 갱신한다. 총괄이 새 보고서를 실제 읽은 뒤 정정된 채팅과 최신 링크를 전달한다. 동료의 행동을 본인 강점에서 빼고 무관한 확인 근거는 유지한다. 이전 revision은 삭제하지 않는다.

표현만 바꾸는 요청은 확인된 사실을 유지하고 기여 표현만 수정한다. 자료를 다시 제출하게 하거나 회사·JD 선택부터 다시 시작하지 않는다. 기본 결과와 실제 후속 수정은 구분해 상태·질문을 맞춘다.
