# 취업 준비 공통 실행 계약

총괄·작업 스킬·담당 사이의 입력, 결과, 상태와 재개 규칙의 단일 원본이다. 각 스킬·담당의 공통 실행 계약 링크로 이 문서를 읽는다.

## 스킬 경로와 개선용 복사본

같은 워크스페이스에서 실제 사용 가능한 스킬 목록과 로드된 지침 경로를 먼저 확인한다. 프로젝트의 Claude Code `.claude/skills/career-os/`, Codex `.agents/skills/career-os/`와 대조하며 사용자 공용 폴더의 동명 스킬을 먼저 고르지 않는다. 프로젝트 사본이 목록에 없다면 파일 존재와 실제 인식을 구분하고 같은 폴더의 새 대화에서 확인한다. 다른 경로가 실제로 로드됐으면 그 차이를 알리고, 읽지 않은 사본을 사용했다고 말하지 않는다.

구조 설명은 확인한 지침을 읽기만 한다. 개선을 요청받으면 사용자가 허용한 개인 위치 중 자동 스킬 등록 경로 밖에 `career-os` 전체 묶음을 복사한다. 하위 스킬·담당·참조 문서의 상대 경로를 유지하고 원본·등록 사본·기존 개인 파일을 덮지 않는다. 같은 입력으로 다시 실행할 때는 수정본 `SKILL.md` 또는 고른 하위 지침의 실제 경로를 직접 지정해 읽고, 필요한 담당·공통 계약도 그 복사본 안의 경로로 전달한다. 이름만 호출해 원본이 선택되게 하지 않으며, 실행한 지침 경로와 결과를 함께 확인한다.

## 입력과 실제 호출

첫 호출에 회사·조건·자료·저장 위치가 없어도 대화로 시작한다. 알려진 답은 재사용하고 미지정 조건은 가정으로 채우지 않는다. 개인 자료는 사용자가 지정한 범위만 읽으며 상위 폴더 전체를 임의 수집하지 않는다. 실행환경의 실제 상위 지침이 필수로 요구한 설정·운영 지침 읽기는 개인 경험 원문 열람과 구분해 기록하며, 그 읽기 자체를 개인 자료 범위 위반으로 보고하지 않는다. 이 구분은 실제 상위 지침에 근거할 때만 적용한다. 파일명이 설정·지침이라는 이유나 담당의 자의적 판단으로 사용자 미허용 문서를 읽을 수는 없다. 필수 설정의 내용은 개인 경험·회사·직무의 사실 근거로 사용하지 않는다. 미허용 개인 경험 원문 열람은 계속 오류로 기록하고 의존 작업을 중단하며 필요한 범위를 요청한다.

위임 입력에는 `task`(company / jd / experience / contribution), 읽을 스킬·담당·이 계약의 경로, 확인한 입력과 결과 참조, 허용 자료 범위, 출력 위치를 전달한다. 독립 호출 도구가 실제로 있을 때만 담당을 호출한다. 역할 이름을 붙인 단일 답변을 독립 위임으로 기록하지 않는다. 기능이 없으면 `delegation_unavailable`을 남기고 단일 실행과 독립 실행을 구분해 보고한다.

반환은 실제 결과 위치, 읽은 출처·원문 위치, 읽지 못한 범위, 남은 질문, 실제 성공/실패와 필요한 조치를 포함한다. 총괄은 반환 파일을 실제로 읽은 뒤에만 해당 결과를 사용한다. 단, contribution 저장 실패 때 실제 반환된 채팅 본문을 사용하는 예외는 아래 기여 반환 계약만 따른다. 담당은 자기 결과만 쓰고 총괄만 브레인스토밍·진행 상태를 갱신한다. 다른 담당의 편집을 덮어쓰지 않는다.

회사 본 조사·공고 탐색 전 현재 도구의 CUA 기능, 연결된 브라우저와 접근 권한 상태를 읽기 전용으로 확인한다. 도구 이름이나 스킬 파일이 있다는 사실만으로 조작 가능을 확정하지 않는다. 확인할 수 없거나 사용할 수 없다면 그 이유와 필요한 환경 준비를 알리고 해당 조사와 후속 작업을 멈춘다. CUA 부재를 웹 검색·학생 수동 원문 수집으로 대체하지 않는다. 준비 확인만을 위해 임의 사이트를 탐색하거나 작업하지 않는다. 브라우저가 준비된 뒤 요청받은 회사·공고 범위에서 실제 조사를 수행하며, 준비 확인을 조사 실행 성공으로 기록하지 않는다.

브라우저 조작은 조사 담당 하나가 소유한다. Drive에 브라우저가 필요하면 총괄이 소유권을 순서대로 조정한다. 동시에 임의 조작하지 않는다. 사용한 도구와 실제 읽은 범위만 기록한다. 검색 요약·미리보기, 원문 열람, computer use 수행은 서로 대체한 성공으로 쓰지 않는다.

## 결과와 저장

저장 위치는 파일 쓰기가 필요해질 때 허용된 위치를 확인한다. 그전 질문·답변은 대화에서 진행하며 파일에 저장했다고 주장하지 않는다. 개인 자료의 원문·결과·상태·호출 기록은 교육 저장소 밖 허용한 로컬 위치에 둔다. 공개 위치에 개인 원문을 복사하지 않는다.

실행 루트의 `revisions/r001/`부터 결과를 저장하고 변경 시 `r002/`처럼 새 버전을 만든다. `progress.json`의 현재 결과 참조만 갱신하며 이전 결과를 삭제하지 않는다.

| 단계 | 결과 이름 | 필수 내용 |
|---|---|---|
| brainstorm | `01-brainstorm.md` | 받은 답·후보·근거·선택 회사·법인 구분·사용자 선택 기록 |
| company | `02-company.md` | 회사·법인·자료 종류·기간·정정·연결/별도 범위·사실·원문 위치·미확인 |
| jd | `03-jd.md` | 후보·선택 JD·업무·필수/우대·모집 상태·마감·확인 시각·원문·채용 법인 비교·보완 참조 |
| experience | `04-experience.md` | 읽기 목록·안정된 경험 ID·역할·행동·결과·출처·중복·충돌·주장별 확인 상태·확인/정정 근거 |
| contribution | `05-contribution.md` | 학생용 설명: 앞세울 경험·JD 업무·기여 해석·보완 근거·출처. 뒤에 요구 ID·확인 주장 ID·정정 의존 관계 보존 |

사실·해석, 미열람·자료 없음, 문서 사실·본인 확인을 구분한다. 공고의 법인·모집 상태, 보고서명·기간·범위와 경험 지표의 의미를 보존한다. 새 수치·역할·자격·인과관계를 채우지 않는다.

## 기여 담당의 반환과 학생 전달

기여 담당은 보고서와 채팅용 결과를 작성하고 실제 저장을 시도한 뒤 다음 필드를 반환한다. 내부 인계용이며 학생에게 JSON을 그대로 보내지 않는다.

```json
{"result_ref":null,"student_result":null,"save_status":"not_attempted","evidence_refs":[],"blocking_question":null,"limitations":[]}
```

- `result_ref`: 실제 저장한 최신 보고서 절대 경로. 실패·미시도면 null. 예정 경로를 성공으로 쓰지 않는다.
- `student_result`: 학생에게 바로 전달할 Markdown 본문. 저장 예정 보고서 링크는 넣지 않고 총괄이 실제 파일을 검증한 뒤 첨부한다. 확인된 본인 행동, 선택 JD의 구체 업무, 기여 가능성의 해석을 연결한다. 관련 회사 근거가 있으면 그 사업·제품·고객·계획이 업무나 경험 활용에 주는 맥락도 짧게 반영한다. 자료에 없는 채용 원인이나 회사 실적을 만들지 않는다. 필수 개인 행동 사실이 부족하면 null.
- `save_status`: saved / failed / not_attempted. progress의 업무 status와 별개다.
- `evidence_refs`: 실제 읽은 `{ref, location, claim_ids}` 목록. 회사·JD에 해당 없는 주장 ID는 만들지 않는다.
- `blocking_question`: 기본 결과에 필수인 질문 또는 null. 선택적 표현 수정은 넣지 않는다.
- `limitations`: 미확인 근거·미열람·실제 저장 오류. 추정 성과는 넣지 않는다.

saved이면 총괄이 실제 최신 파일을 읽어 선택 JD·현재 confirmed 주장·반환 본문을 대조한 뒤 채팅용 결과와 그 파일 링크를 전달한다. 파일을 저장하거나 상태를 complete로 적은 것만으로 사용자 전달 성공이 되지 않는다.

failed이면 실제 반환된 student_result만 채팅으로 전달하고 보고서 저장 실패를 밝힌다. 이것만 파일 읽기 규칙의 예외다. 총괄이 반환 없는 본문·성과·보고서를 만들거나 다른 위치로 우회해 성공으로 바꾸지 않는다. 링크를 만들지 않는다.

확인 행동이 없으면 not_attempted, student_result=null과 필수 사실 질문을 반환한다. 계획·pending·conflicted 행동으로 강점을 채우지 않는다. 실제 반환이나 파일이 없는데 미래 작업을 완료했다고 설명하지 않는다.

| 실제 관찰 | 상태와 응답 |
|---|---|
| 확인 행동으로 작성·저장·총괄 읽기 성공 | current_stage=contribution, contribution.complete, 최신 result_ref, pending_question=null. 의미 있는 채팅 본문과 실제 보고서 링크 전달 |
| 저장 실패, 실제 반환 본문 있음 | current_stage=contribution, contribution.blocked, 이번 result_ref=null, pending_question=null. 본문 전달과 저장 실패 고지 |
| 확인 행동 없음·필수 사실 답변 필요 | current_stage=experience, experience.awaiting_user, contribution 미완료. 필수 확인 질문만 전달 |
| saved 반환 파일이 없거나 읽기·최신성 확인 실패 | contribution.blocked. 검증 안 된 파일을 최신 result_ref로 확정하지 않음. 확보한 범위와 실패를 전달 |
| 기본 결과 완성 뒤 표현 수정만 선택 | contribution.complete, pending_question=null. 선택적 수정 안내로 끝내고 의무 확인 턴을 만들지 않음 |

complete는 내용·파일 준비가 확인된 상태다. 실제 채팅·링크·열람 증거는 별도로 검증한다. 저장 실패 때 기존 성공 보고서는 보존하되 이번 정정 결과인 것처럼 다시 링크하지 않는다.

## 진행 상태

실행 루트 `progress.json`은 다음 필드를 갖는다.

- `schema_version`: `2`
- `run_id`: 실제 실행 식별자
- `environment`: 실제 도구·독립 호출 가능 여부·파일 로드 또는 제품 등록 등 관찰 환경
- `current_stage`: brainstorm / company / jd / experience / contribution
- `stages`: 위 다섯 키. 각 값은 `status`, `input_version`, `result_ref`를 포함하며 미생성 결과 참조는 null
- `input_refs`: 실제 입력·원문·버전 참조
- `pending_question`: 사용자 선택·회사 구분·JD 선택·경험 확인 등 현재 답을 기다리는 질문. 없으면 null
- `dispatches`: 실제 담당 이름, 작업, 호출 종류·순번, 입력 참조, 반환 위치, 반환 확인 여부. 미호출 작업의 호출 ID를 만들지 않음

질문을 하기 전에 `current_stage`와 `pending_question`을 실제 기다리는 단계·필요한 답에 맞춘다. 회사 조사 뒤 관심 업무를 묻는 것은 JD 탐색을 위한 대기이고, 공고 선택 뒤 자료 범위를 묻는 것은 경험 단계의 대기다. 답을 받으면 해당 질문에 연결해 재사용하고 해소된 질문을 비운다. 이전 단계에서 받은 회사·JD·자료 범위를 다시 묻지 않는다. 화면에는 내부 키 대신 총괄에 정한 단계 이름과 필요한 행동만 보여준다.

기여 결과는 이번 미션의 결과이며 최종 자기소개서나 실제 기업 지원 제출과 다르다. 사용자가 경험 사실을 정정하면 경험 담당의 갱신과 해당 근거에 의존한 기여 결과 수정으로 돌아간다. 해석·표현의 수정은 확인된 사실 범위에서 다듬고 별도 기능 제작이나 지원서 작성으로 확장하지 않는다.

`dispatches`의 호출 식별자는 도구가 실제 반환한 값으로만 기록한다. `collaboration.spawn_agent`가 canonical `task_name`만 반환하면 그 문자열을 `agent_name`에 그대로 저장한다. `operation`은 `spawn` 또는 `followup`, `invocation_index`는 실행 내 실제 호출 순번으로 별도 저장하고, 제공되지 않은 `tool_call_id`는 null이다. 같은 담당을 다시 호출해도 canonical 이름에 `:jd`, `:spawn`, `followup_task:` 같은 접두사·접미사를 붙이지 않으며 호출 UUID도 만들지 않는다. 호환을 위해 `call_id`를 유지한다면 도구 호출 ID가 아닌 실제 canonical 담당 이름의 별칭임을 `environment.call_id_semantics: agent_name_alias`로 밝히고 `agent_name`과 같은 문자열만 저장한다. 담당의 반환에서도 실제 담당 이름과 작업·반환 위치를 분리한다.

업무 `status`는 `not_started / running / awaiting_user / blocked / complete`다. 도구가 없으면 `environment`에 `delegation_unavailable`을 기록하고 독립 호출 성공으로 처리하지 않는다. 후보 탐색을 했어도 회사 본 조사 단계는 `not_started`이며 회사 선택 대기는 brainstorm의 `awaiting_user`다. 회사가 모호할 때도 같은 원칙을 적용한다. 사용자 선택·본인 확인·인증 대기를 자동 재시도로 대신하지 않는다.

출처 읽기 상태와 경험의 `pending / confirmed / conflicted`는 결과 파일에서 별도로 관리한다. 경험의 역할·행동·수치 각각에 확인·정정 근거를 붙인다. 한 행동을 확인한 답변으로 충돌 수치까지 confirmed로 올리지 않는다. 단계 완료는 모든 경험 주장이 확인됐다는 뜻이 아니다. 정리 담당은 confirmed인 주장만 기여 근거로 쓰고 나머지는 확인 대상으로 남긴다. 테스트 판정(미실행·통과·실패·차단·정보 보완)은 업무 상태와 별개다.

## 오류·변경·재개

같은 원인은 최대 두 번 재시도한다. 실패 이유·마지막 성공 결과·필요 조치를 보존한다. 로그인·CAPTCHA·권한 문제는 사람이 해결할 조치로 반환하며 자료 없음으로 바꾸지 않는다. 선행 결과가 막히면 그 결과에 의존하는 단계도 진행하지 않는다.

회사 변경은 company/jd/contribution을, JD 변경은 경험의 요구 대조와 contribution을, 경험 정정은 해당 경험과 연결된 contribution을 다시 확인한다. 같은 자료 범위의 확인 경험 원문 추출은 재사용한다. 새 문서가 추가되면 해당 경험과 그에 의존하는 결과를 갱신한다.

새 대화에서는 스킬·progress.json·참조된 실제 결과·원문 버전을 다시 읽고 재사용 가능 여부를 판단한다. 읽을 수 없거나 위치가 없으면 필요한 자료를 요청한다. 이전 대화를 기억하거나 파일을 읽었다고 주장하지 않는다. 실제 지원 제출·원본 덮어쓰기·학생 최종 확인을 대신 수행하지 않는다. 실제 호출·반환·저장·재개가 관찰된 환경과 범위만 완료 증거로 보고한다.
