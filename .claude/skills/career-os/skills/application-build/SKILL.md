# 기여도와 강점 정리

먼저 [공통 실행 계약](../../references/runtime-contract.md)을 읽는다. 공고의 요구, 회사 사실, 본인이 확인한 행동을 연결한다. 기본 결과는 `05-contribution.md`다.

## 입력

- 선택 공고와 모집 상태, 회사 조사 결과 및 원문 위치.
- 경험 ID·주장 ID·출처, 주장별 pending·confirmed·conflicted 상태와 실제 확인·정정 기록.
- 저장 경로와 기존 기여 결과(있으면).

문항·글자 수는 기본 입력이 아니다. 자소서를 명시적으로 요청했을 때만 실제 문항·분량을 확인한다.

## 절차

1. 입력 결과를 읽고 법인·직무·기간·주장별 확인 상태를 보존한다.
2. 요구별로 confirmed인 개인 행동만 연결한다. 경험 ID·주장 ID·문서 위치와 실제 본인 확인 출처를 함께 남긴다. 자료 없음과 미열람은 구분한다.
3. 회사 자료에서 선택 직무에 관련된 사업·제품·고객·사업 계획의 사실을 1~2개 고른다. 그 사실이 JD 업무의 쓰임이나 확인 경험의 활용을 어떻게 구체화하는지 설명한다. 회사명·출처만 붙이거나 JD 내용을 회사 사실인 것처럼 반복하지 않는다. 회사 자료가 부족하거나 해당 업무와 연결할 근거가 없으면 그 한계를 상세 근거에 남기고 JD에서 확인한 업무 범위로 정리한다. 맥락을 만들지 않는다. 강점·기여와 회사 사실의 직무 연결은 해석이며, 채용 이유·출시 완료·본인 실적·입사 후 성과로 확정하지 않는다.
4. 대응 경험이 없는 요구는 부족한 근거와 필요한 질문을 남긴다. 필수·우대를 유지하고, SQL 등의 근거 미제공을 능력 없음·자격 없음으로 바꾸지 않는다.
5. pending·conflicted 주장과 미해결 수치·기간·역할은 확인 대상에 따로 남긴다. confirmed 행동 하나로 같은 경험의 다른 주장까지 확인 처리하지 않는다.
6. 정정된 경험 결과가 들어오면 이전 기여의 의존 주장 ID를 대조해 그 행동을 사용한 강점·기여를 철회하거나 갱신한다. 정정 전후와 유지한 근거를 남기고 기존 결과는 보존한다. 경험 확인 상태 변경은 경험 담당에게 인계한다.

## 사실 기준

- 수치·역할·자격·기간·인과관계를 새로 만들지 않는다.
- 팀 결과를 개인 성과로 바꾸거나 지표의 의미를 변경하지 않는다.
- 문서의 목표·계획을 달성 결과로 쓰지 않는다. 문서에 있는 수치도 본인 확인 전에는 기여 근거가 아니다.
- 회사 사실은 업무 맥락에만 쓰고 개인 역량·채용 의도로 바꾸지 않는다.
- 적합도 점수·합격 확률·기여 비율을 임의 계산하지 않는다.
- 본인 확인이 끝났어도 지원서 최종 확인·제출 완료로 기록하지 않는다.

## 학생에게 읽히는 결과

보고서 앞에는 아래 학생용 설명을 놓고, 뒤에는 상세 근거 기록을 보존한다. 학생에게 설명하는 순서는 먼저 보여줄 경험, 함께 보여줄 경험, 우선 보완할 근거다. 내부 ID나 큰 대조표를 첫 화면에 두지 않는다.

### 학생용 채팅 결과

`student_result`는 학생이 채팅에서 읽을 완결된 결과다. 보고서 전체나 앞부분을 길게 복사하지 않는다. 다음 흐름으로 작성한다.

1. 첫 문장에 선택 회사·직무와 연결한 **기본 강점 정리를 마쳤다**고 밝힌다. 회사·직무는 알아볼 이름으로 쓰고 내부 공고 ID는 넣지 않는다. 자소서 작성·지원 제출 완료와 구분한다.
2. 먼저 보여줄 경험 한 가지를 정한다. 그 경험을 설명하는 한 단락 안에서 **확인한 본인 행동 → JD의 구체 업무 → 그 행동을 어떻게 활용할 수 있는지**까지 잇는다. 관련 회사 근거가 있으면 제품·고객·사업 맥락이 이 업무나 경험의 활용에 주는 의미를 한두 문장으로 연결한다. 회사 개요를 길게 되풀이하지 않는다. 경험을 소개한 뒤 별도 ‘기여 가능성’ 절에서 같은 경험을 다시 설명하지 않는다.
3. 함께 보여줄 경험도 각 설명 안에서 행동·업무·활용을 끝낸다. 2~3개는 권장 범위다. 하나만 확인됐으면 하나를 충분히 설명한다. 관련 없는 두 활동을 한 성과나 하나의 인과관계로 합치지 않는다.
4. 기본 결과 뒤에 **더 보완한다면 먼저 확인할 근거 1~2개**만 고른다. 선택 공고의 필수 조건과 확인 근거 사이에서 판단을 바꾸는 정보를 앞세운다. 한 항목에 경력·언어·운영 범위나 배포·복구·정책처럼 여러 사실·사례를 묶어 두 항목인 것처럼 쓰지 않는다. 선택한 근거를 어떤 기존 자료로 보완할지 알려준다. 그 외 미확인 내용은 상세 기록과 limitations에 남긴다.
5. 끝에는 표현을 고치는 것이 선택임을 한 문장으로 알린다. 기본 정리를 마쳤는데 ‘맞나요?’, ‘계속할까요?’로 답을 요구하지 않는다.

각 문장은 학생이 사용할 설명을 바로 쓴다. ‘이 경험을 강점으로 제시하면 좋다’는 작성 방법, 이미 말한 행동을 다른 말로 반복하는 문장, 매 단락의 같은 해석 안내는 덜어낸다. 그 경험의 의미를 바꾸는 한계는 해당 단락에 붙이고, 그 외 확인 대상은 전부 채팅에 나열하지 않는다. 자료에 없는 수치·역할·기술·설계를 보태 간결하게 만들지 않는다.

`student_result`에는 보고서 저장·열람 성공을 전제로 한 문장이나 예정 보고서 링크를 넣지 않는다. 총괄이 실제 파일 읽기와 저장 상태를 확인한 뒤 출처·보고서 안내를 붙인다. confirmed 행동이 있어 기본 정리가 가능하면 추가 수치·문항을 필수 답변으로 기다리지 않는다. 확인 행동이 없을 때는 공통 계약대로 필수 사실 질문을 반환한다.

### 상세 근거와 반환

보고서 뒤에는 사용한 회사 사실의 출처·기간과 그 사실에서 해석한 업무 맥락을 구분해 남긴다. 요구 ID·필수/우대, confirmed 경험 ID·주장 ID·개인 행동·원문 위치·본인 확인 출처, pending/conflicted 목록, 정정 전후·의존 관계를 보존한다. 선행 경험 기록 참조도 남긴다. 읽기 쉬운 본문을 위해 추적 근거나 미확인 사항을 삭제하지 않는다.

문항·연습문항·자소서 문단은 자동 생성하지 않는다. 명시적 자소서 요청 시에만 별도 초안을 만들며 실제 문항 미열람이면 그 사실을 밝힌다. 미확인 주장을 최종 근거로 넣지 않는다.

저장은 공통 계약의 새 revision을 사용한다. 원문·선행 결과·다른 담당 결과·progress.json은 수정하지 않는다. 반환 구조·저장 실패 본문 전달·상태 처리는 공통 계약의 ‘기여 담당의 반환과 학생 전달’ 한 곳을 따른다. 실제 작성한 채팅용 결과를 반환하며 저장 실패만으로 그 본문까지 누락하지 않는다.

## 중단과 재개

- 공고·회사·경험 결과가 없으면 빠진 입력과 수행 가능한 범위만 반환한다.
- confirmed 행동이 일부 있으면 그 범위의 기여를 정리하고 나머지는 확인 대상으로 남긴다. 모든 수치 확인이나 자소서 문항을 기다리며 기본 정리를 막지 않는다.
- 충돌이 핵심 주장을 바꾸면 해당 주장을 기여 근거에서 제외하고 확인 질문을 남긴다.
- 재개할 때 입력의 변경 여부를 읽고 바뀐 근거에 의존하는 결과만 갱신한다.
